1. The problem

MANA splits each MPI rank into an upper half (the application, checkpointed) and a lower half (the MPI library and network, thrown away at checkpoint and re-created at restart). A CUDA-aware MPI puts a second CUDA user in the process: the MPI's UCX reads and writes the application's device buffers. Four facts, all verified on this machine, shape the design:

  • One CUDA driver per process. NVIDIA's checkpoint API (cuCheckpointProcess*) handles one driver instance. With an MPI that loads its own libcuda in the lower half, the API checkpointed the MPI's driver and ignored the application's GPU state.
  • The lower half is replaced at restart, so no CUDA state may belong to it.
  • CUDA IPC handles do not survive a checkpoint. A live legacy export (cuIpcGetMemHandle) makes the checkpoint fail (304) and the process die; a VMM POSIX-fd export can be checkpointed, but importers must hold no mapping, and an old handle maps the old memory after restore.
  • The GPU restore needs running threads (it hangs before DMTCP resumes them) and the driver's original address-space layout.

2. Architecture

The application's CUDA driver is the only one. The lower half's CUDA libraries are generated forwarding shims: every call from UCX or MPICH jumps into the upper half's real library, with the thread's upper-half TLS. UCX therefore uses the application's context and device pointers, exactly as in a native process, and the DMTCP CUDA plugin checkpoints that one driver.

A forwarded call

Each shim symbol is a two-instruction trampoline into a common entry. It needs no function prototypes, leaves stack arguments in place (cuLaunchKernel's 11 arguments pass through), and finds the calling thread by its stack pointer, so no system call is involved. Functions that hand out pointers or tables (cuGetProcAddress, cuGetExportTable, kernel registration) get small hand-written wrappers.

3. CUDA IPC with virtual handles

Intra-node GPU-to-GPU transfers use CUDA IPC. The shim gives the MPI virtual IPC handles, the same idea as MANA's virtual MPI ids. UCX only ever sees a handle naming (exporter pid, fd number, size) and the address where the shim mapped the peer's buffer. The real export and mapping behind them are dropped before each checkpoint and re-created after it, at the same fd number and the same address. UCX's IPC cache therefore stays valid, and stays on.

The VMM allocator (upper half)

The driver's exported entry points are stubs: cmpl, je, call *slot(%rip). libmana_cuda_vmm.so decodes the stub and writes its wrapper into the slot of cuMemAlloc_v2, cuMemAllocPitch_v2 and cuMemFree_v2. This is one pointer store, with no code patching, and it catches a statically linked cudart and cuGetProcAddress users too.

Allocations of 1 MB and larger get their own VMM allocation. Smaller ones are carved out of 2 MB VMM chunks, first fit, 512-byte aligned.

How UCX is steered

UCX's cuda_ipc asks one pointer-attribute question per buffer. If the answer to IS_LEGACY_CUDA_IPC_CAPABLE is yes, it calls cuIpcGetMemHandle. The shim answers yes for VMM POSIX-fd memory, so UCX lands in the virtual handles. For real cudaMalloc memory it answers no, because a real legacy export would make the process impossible to checkpoint.

The same handles should serve Cray's GTL, which also speaks legacy IPC.

4. Checkpoint, resume and restart

DMTCP runs pre-checkpoint hooks in plugin order (MANA first) and resume/restart hooks in reverse order (the CUDA plugin first). The design uses that order. MANA's lower-half gate keeps application threads out of MPI while the shims and MPI state are not ready; their CUDA calls wait on the CUDA lock.

7. Limits and next steps

Open items

  • CUDA calls from threads that the lower half creates get "no device" (none seen with UCX); fix with an upper-half proxy thread.
  • Small allocations share a chunk: an IPC export exposes neighbors within the process; up to 2 MB extra per device.
  • UCX's memory hooks warn on suballocated frees natively (they are off under MANA).
  • CUDA objects of an old lower half are restored and leak at each restart (small).
  • Multi-GPU peer access, other drivers' UVA layout: to verify.
  • Ask NVIDIA about legacy-IPC support in the checkpoint API.

Perlmutter (Cray MPICH)

  • Check cuCheckpointProcess* with plain DMTCP on the A100 nodes.
  • Regenerate the shims for libcudart.so.12; list what GTL loads.
  • GTL uses legacy IPC: verify the virtual handles and allocator apply unchanged.
  • 4 ranks per node, one GPU each; GPU binding at restart.
  • Main risk: inter-node GPU RDMA registers device memory with the NIC. Whether the checkpoint API accepts that is unknown; if not, release registrations after the drain, like the host registrations.
